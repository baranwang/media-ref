# 0004 让告警和锁自动走到终点

状态：草案（2026-11-27）

## 背景

[项目宪法第三节](../../CONSTITUTION.md)列出了仍需人介入的地方。[ADR 0003 修订](0003-review-agent.md)解决了变更单的判定。驳回一张挑战锁定关联的变更单，原关联仍然锁定，`review_alerts` 里也仍有一条未关闭的告警。下文针对这些数据和告警提出方案，由维护者在改规则时取舍。

## 拟议决定

每类告警由下列任务处理。定时任务补排漏掉的开放告警，任务按目标和证据版本去重。建议每轮最多取证三次，临时故障退避重试，到限采用各节的保守结论。写回前在事务内核对目标、版本和相关证据是否仍有效；已被取代的告警记为过时并关闭。每次结案都记录目标、证据、规则版本、尝试次数、结论和理由，和数据变更一起提交。证据或规则有变化才另开一轮，避免同一事实反复开单。

### 1. 重复媒体

目录组探索在 `exploration-agent.ts` 发现 TMDB、TVDB 或 Trakt 编号已属另一部媒体时产生 `agent_external_id_conflict`。建议由合并任务重取双方的权威目录证据。用一方的 IMDb 编号反查 TMDB，须恰有一个同类型结果；核对该结果回指同一 IMDb、另一方的目录条目也指向它，再比对双方快照的标题、年份、类型，以及剧集的季号和各季集数。缺项、相互矛盾、存在止损锁或迁移后段冲突，都以「保留两部媒体」结案。

全部通过才以持有已核实 TMDB 编号的媒体为目标，在同一事务重新检查归属并执行 `mergeMedia`，关闭这条冲突告警。记录源和目标 ID、两条身份链、迁移前后的外部编号、变体、关联及段，连同重定向保存。误合并会让原有查询指向另一部媒体，拆回还涉及已迁移的历史。严格核对会漏掉快照不全的重复媒体，代价较小。

### 2. 审核员直接写入

`apps/api/src/reviewer.ts` 有六个仍可写入业务数据或告警的审核员 RPC。`approveChangeRequest` 和 `rejectChangeRequest` 已返回 409；`setUserRole` 经 `requireOwnerAuth` 管理账号，不判定媒体数据。

| RPC                       | 建议处置及理由                                                                                  |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| `setAssociationLock`      | 限为止损。按第 3 节临时阻止已知错误的替换，避免误锁长期挡住正确变更。                           |
| `overrideMediaExternalId` | 删除。改错编号会把外部键查询导向错误媒体，由目录同步或第 5 节核实后写入。                       |
| `setMediaExternalIdLock`  | 限为止损。短期阻止坏上游覆盖正确编号，误锁由第 3 节到期解除。                                   |
| `mergeMedia`              | 删除人工入口。仅在第 1 节核实后调用核心合并事务，避免跳过身份核验。                             |
| `switchMediaBaseline`     | 限为止损。切换前核对新基准，写入时记录受影响的段并安排第 6 节任务，防止旧集号被当成新集号使用。 |
| `resolveReviewAlert`      | 删除。它只写关闭状态、时间、操作人，误关会掩盖仍在发生的问题。由对应任务写入结论并关闭。        |

`conflict-resolution.ts` 中的两个锁操作和覆盖外部编号都没有写修订记录。拟保留的入口每次须说明止损原因及对应的规则修复，和数据在同一事务记录操作人、时间、目标、前后值和受影响的版本；记录失败则整次回滚。止损操作结束后，数据由定时任务继续核对。直接删除 `proto/mediaref/v1/reviewer.proto` 中的方法会破坏已发布的 `@media-ref/client` 1.0.0。建议先弃用并在旧入口返回明确的停用原因，下一个主版本再移除定义。

### 3. 锁没有期限

`media-service.ts` 在提交时、`evidence-job.ts` 调用 `conflict-resolution.ts` 在取证或批准遇锁时，都会产生 `locked_association_challenged`。拟由锁复查任务读取被挑战的关联、锁的理由和变更单结果。有效止损期内保留原值并关闭这次挑战；有新的反证可单独提出变更单。这样即使挑战有理，也可能延后一次正确替换。

止损锁须有到期时间，旧锁也要在迁移时分配有限期限。到期任务只解除本次锁，保留原数据并重新取证，记下锁的创建、期限、解除和核对结果；证据不足就保留原值结案。提前解锁可能重新引入上游错误，所以解锁本身不触发无条件覆盖。现有锁约束替换、撤下关联和同步覆盖已有外部编号；失效复查仍可更新锁定关联的展示快照、标记内容不符，TMDB 同步也可标记锁定关联的段。

### 4. 锁定关联已下架

`invalidation.ts` 的失效复查在平台明确返回 `not_found` 且关联有锁时产生 `locked_association_delisted`。建议自动复查任务隔时再取同一合集。仍明确下架时，在锁到期后核对关联版本，再按现有撤下路径写 `delisted` 修订并重新开放需求；合集恢复且身份核对通过则保留。只有超时、限流或矛盾证据，到限保留原状并关闭告警，注明无法证实下架。逐次记录平台回答和版本，防止把临时故障当成永久下架。

### 5. TMDB 编号失效

`tmdb-sync.ts` 的每日同步遇到 404 产生 `tmdb_missing_or_merged`。现有 `mergeMedia` 会顺带关闭源媒体的这类告警，但它只由审核员调用。建议同步任务延时重查原编号；恢复就刷新并关闭。仍为 404 时用独立的 IMDb 身份链和快照查替代条目。唯一匹配且无锁才替换编号；新编号已属另一部媒体时按第 1 节核实。未找到、候选冲突或到限，保留旧编号及最后快照，记录「上游未确认」并结案，同一 404 不再开单。这样可能暂留失效的编号，但不会因一次 404 把翻拍剧接到原剧。记录原编号、候选项、上游答复及采用或保留的理由。

### 6. 段的坐标待核对

`tmdb-sync.ts` 在季结构变化、合并后段的基准不符、切换基准时产生 `segments_needs_review`。建议任务按媒体枚举所有已标记段，逐段重取当前基准的分集和平台正片列表，比对标题、顺序及段边界。对应唯一且范围核验通过，才清除该段标记；需改坐标则经变更单生效。无法对齐或变更单被驳回，到限以「不提供这些段的按集定位」结案，继续仅返回合集；保留可用的其他段。误清一个标记就可能让整段错一集。保存两份分集证据、段的前后坐标和逐段结论，所有受影响段都有结论再关闭告警。

### 7. 种子取证失败

`seeds.ts` 的 `markSeedEvidenceFailedInTx` 产生 `seed_evidence_failed`。原排队逻辑跳过已标记的种子，同一种子的历史任务也会阻止重排。建议由种子复查任务直接取证：通过原证据门才确认并清除种子标记；身份冲突或到限仍取不到证据，终止本版种子并从可查询候选中撤下。两种结果都写关联修订、证据门结论及告警处理记录。暂时不可达可能使正确种子被撤下，保留导入来源和历史供新证据触发新一轮取证。

### 8. 关联内容不符后的复查

`invalidation.ts` 对已确认关联重新执行证据门第一步，内容不符时产生 `association_content_mismatch`。只有同一修订重新通过原检查、关联未锁定、且能证明内容失配设置了关联标记时，复查才在同一事务内恢复。关闭告警只是结束提醒；新告警的归因只能用于恢复一次，即使先由账号关闭，也保留其关闭时间和操作人。升级前已手动关闭且记录了修订号的告警，没有一次性恢复记录；若已有可能消耗该证据的旧成功复查，则不凭这条告警清标记。段的标记与 TMDB 告警独立，第一步通过不会恢复这些段的按集定位。

缺修订号的旧告警不能在首次通过时恢复。只有再次发现失配，且唯一开放告警（已手动关闭时，须是该关联历来唯一的同类告警）记录了同一合集、原检查原因，并能对应同一关联已完成的失配任务，才尝试核实来源：该关联必须只有创建时已确认的第一条修订，且变更单实际写入的正是该关联和修订。这样才把新的失配证据绑定到当前修订，等下一次通过再恢复。不按时间猜修订，不批量补历史；证据不足或属于另一修订，继续降级。没有新的失效上报，目前未必会再次触发复查。

建议由该告警主动排下一次失效复查，记录取证版本、平台结果和冲突项。恢复时按上述条件结案；证实仍是另一部媒体时按当前版本撤下关联并记录修订，有止损锁则在到期重新核对后执行。到限仍无法判明则保留降级并以「无法确认内容」关闭告警。把一次平台异常当成永久变化会误撤正确关联，贸然恢复则会向客户端返回错误集号。

## 未决问题

- 对历史疑似重复媒体回放身份核验时，会误合并多少同名翻拍、错季或上游串号的媒体？自动写入前需要哪些样本验证？
- 三次取证之间应间隔多久，旧锁和新止损锁的最长期限各是多少？需要各平台的故障恢复时间和现有锁龄分布。
- 哪些客户端还依赖这六个写入口，停用行为和下一主版本如何排期？
