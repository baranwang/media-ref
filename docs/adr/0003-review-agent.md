# 0003 审核 agent：自动判定没过证据门的变更单

状态：草案（2026-11-26）

## 2026-11-27 修订：没有人工（依据 CONSTITUTION.md）

项目没有审核员，下文凡是「维持人工」「留给审核员」的地方，一律按本节执行，以本节为准：

- **每张 `needs_review` 都排审核任务。** 不管它是怎么变成 `needs_review` 的（证据门冲突、和已有关联冲突、锁定、证据缺失、Tier 1 平台），
  标记时就在同一事务里排任务；cron 每分钟再扫一遍，把没有活动任务的 `needs_review` 补排上。
- **审不了的直接驳回，不调模型。** 只有证据门自己的冲突（`conflict_reason` 就是证据门的第一个冲突码，且没有 `shared_id_conflict`）
  才交给模型；其余（第 1 节原来「直接留给审核员」的那些，加上和已有关联的冲突 `new_failed_old_passed`、`both_passed_evidence_gate` 等）
  直接驳回，理由写明原因，不占当天的审核额度。
- **三种结论改为：放行、驳回并改正、驳回。** 「维持人工」改成「驳回」（附模型的意见）。模型没给结论、步数或 token 用完、
  放行或改正没过代码复核、批准时出错，一律驳回。驳回后需求按没找到退避，探索 agent 之后会再找。
- **故障重试，不驳回。** 模型调用失败（没有结论时）或目录取不到，任务一小时后重试；当天审核额度用完，任务排到下一个 UTC 日。
- `REVIEW_AGENT_DAILY_BUDGET` 开到 200。第 7 节的 `/review` 队列只剩查看用途，不是流程里的一步。
- 网站（第 7 节）：变更单页和进度里，审核 agent 的驳回显示为「审核 agent 驳回」并附理由；`needs_review` 显示为等审核 agent 判定，
  不再说等审核员。`/review` 不再有「审核 agent 的意见」一栏（没有维持人工的单了）。

## 2026-11-27 修订二：人通过留言参与

宪章说维护者不介入运行，也说欢迎外部参与、外部输入是证据不是决定。人不在流程里，但可以参与：
**对变更单留言，由审核 agent 照着去做**。留言可以简单到「通过」「驳回」，也可以是「第 7 集起错开一位」
「这个合集其实是第二季」。本节以上一节为基础，冲突时以本节为准。

- **人不再直接改变更单状态。** 审核员接口的批准、驳回变更单不再生效，返回「变更单由证据门和审核 agent 判定，请留言」。
  `/review` 和变更单页的「通过」「驳回」按钮保留为快捷方式：预填一条「通过：」「驳回：」开头的留言发出去。
- **谁能留言。** 登录用户都能留言（不限审核员），每人每天有条数上限。API key 不能留言。留言公开显示在变更单页。
- **每条留言都排一次审核会话。** 留言就是这次会话的指令。同一张单同时只有一个审核任务；会话开始时读这张单所有还没回复的留言，
  一起回复。cron 补排有未回复留言、又没有活动任务的单。每张单每天最多因留言跑 3 次会话；留言触发的会话占当天的审核名额。
  变更单还在 `pending_evidence` 时，留言等取证结束、进入审核时一起读。
- **照做之前先核实。** 提示词说明：留言是有人这样要求，可能对也可能错，要自己拉合集和季核实；核实得了才照做。
  照做的结果过的代码检查和原来一样（放行要本次会话拉过合集和每一季、每个冲突码一条理由；改正要过复核）。
- **按变更单状态，能做的事：**
  - `needs_review`、`rejected`：放行、驳回、驳回并改正。已驳回的单再驳回，就是维持驳回，不再让需求退避一轮。
    已驳回的单放行时，从 `rejected` 批准，走同样的批准路径和锁定检查。
  - `approved`：维持、撤下、撤下并改正。撤下把这张单生效的关联标成 `delisted`，写一条关联修订（操作人是审核 agent，
    理由里带留言和核实结果），并让对应季的需求重新开放（撤下并改正不退避，并写线索，同第 4 节）。已锁定的关联不能撤下。
    撤下的代码检查：本次会话拉过合集和每一季，并写了理由。
- **agent 每次都回复。** 每次会话结束，在留言下写一条审核 agent 的回复：结论是什么、做了什么、哪些要求没照做、为什么。
  没有留言的审核（证据门转来的）也照常把结论写进同一个对话，变更单页把留言和回复按时间显示成一段对话。
  模型出错要重试时，先不回复，重试完再回复。

存储：新表 `change_request_comments`（变更单、作者，`system:review-agent` 表示 agent 的回复、内容、回复的是哪几条留言、
时间）。`evidence.reviewAgent` 仍然记最近一次的结论。

## 背景

变更单取证后，证据门（`evidence-gate.ts`）全部对上就自动生效，否则标成 `needs_review`，
等审核员在 `/review` 处理。证据门是逐项比对的规则，只要有一项对不上就转人工，
其中不少是对的单。2026-11-26 线上卡住的四张单：

| 变更单                      | 卡在                                  | 实际                                                                                                     |
| --------------------------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 诛仙 最终季（腾讯）         | 第一步片名：「诛仙」对「诛仙 最终季」 | 对。去后缀只认「第N季」等，不认「最终季」                                                                |
| 妻子的浪漫旅行2026（芒果）  | 第一步片名：多了「2026」              | **季号错了**：提交第 6 季（2022 年、13 集），应为第 8 季（2026 年、14 集）                               |
| 咒术回战 第二季（哔哩哔哩） | 第一步年份：2020 对 2023              | 对。TMDB 把 59 集放在一季，年份按季首播比，应按提交的第 25–47 集比                                       |
| 灵笼 第一季（哔哩哔哩）     | 第一步集数：TMDB 12 集，平台 16 条    | 合集和季对。平台把中章、终章上下、特别篇混在正片里，TMDB 放在第 0 季；中章夹在中间，分段要拆开（见 6.1） |

四张都在第一步失败，第二步（逐段核对季、集、年份、默认版本）一次都没跑。

由此得出：

- 有一部分是规则漏洞（片名后缀、片名尾的年份、按段比年份），改规则就能自动生效，不需要模型。
- 灵笼这类是**平台和目录归类规则不同**：数字对不上，但读一遍分集标题就知道多出来的是什么。
  规则写不完这类情况，需要判断。
- 判断也要能发现提交本身错了（妻子的浪漫旅行），不能只会放行。

## 决定

### 1. 审核 agent 的位置

证据门之后、审核员之前。变更单转成 `needs_review` 时排一个审核任务，人工提交和探索 agent 提交的都走。
审核 agent 用 `system:review-agent` 用户（和 `system:exploration-agent` 一样由代码确保存在），
它的决定写进 `reviewer_user_id`。

不排任务、直接留给审核员的情况（审了也不能放行，省掉模型调用）：

- `shared_id_conflict`：共同外部编号指向别的作品；
- 锁定冲突（`locked`）；
- 证据缺失：`catalog_not_found`、`collection_not_found`、Tier 1 适配器（`adapter_tier_1_manual_review`）。

### 2. 三种结论

每张单以唯一的结论工具结束，三选一：

- **放行**：批准，关联生效。
- **驳回并改正**：提交有错，且 agent 给出改正（见 4）。
- **维持人工**：其余情况，附上意见，单子留在 `/review` 队列。

模型没给结论、预算用完或运行失败，一律算维持人工。

### 3. 放行的条件（代码检查）

模型说放行不算数，代码依次检查，任一不满足就改为维持人工：

- 证据门的冲突里没有第 1 节列出的那些；
- 本次会话里实际调用过 `get_collection`（这个合集）和 `get_catalog_season`（提交涉及的每一季），
  不能只凭变更单上已有的证据；
- 每个冲突码都有一条理由，例如「平台多出的 4 条是中章、终章上下、特别篇，TMDB 放在第 0 季」。
  理由存进 `evidence.reviewAgent`。

批准走现有的 `approveChangeRequestInTransaction`，`enforceUnlockedCheck` 照旧。

### 4. 驳回并改正

agent 认为提交错了时，必须给出改正后的季和分段。代码用已拉到的目录和合集复核改正，
通过了才允许驳回，否则维持人工（意见里写上它的判断）：

- 第一步：只允许集数类冲突（`episode_count_*`），片名、类型、共同编号、年份对不上都不行；
- 第二步：额外内容夹在正片中间时，正确的分段在平台位置上会跳过几位、总数也和合集不等
  （灵笼：第 1–6 集对位置 1–6，第 7–12 集对位置 8–13，16 条对 12 集）。所以只要每一段都落在合集的正片范围内、
  各段在平台位置上互不重叠，就不计 `target_episode_start_mismatch` 和 `segment_episode_count_mismatch`；
  第二步的其他冲突照样拦。

驳回时在同一事务里：

- 以 `rejectChangeRequest` 驳回，理由写明错在哪、改正是什么；
- 写一条**线索**：同一媒体、命名空间、平台编号，改正后的季号，备注写理由。上报人 `system:review-agent`；审核 agent 没有 API key，`reporter_key_id` 填常量 `REVIEW_AGENT_KEY_ID`（值同为 `system:review-agent`，这一列没有外键，不改表）；
- 确保这一季在该命名空间组有一条可以立即探索的需求：变更单本来就关联了需求的，把它重新打开且**不计入没找到、不退避**
  （`reopenDemandAfterRejectionInTx` 增加这个分支）；人工提交的单没有需求，就新建一条。

之后探索 agent 照常处理这条需求：线索进入候选集合，改正后多半能走快速通道，不调用模型，直接进证据门。

不让审核 agent 自己提交改正后的单：那样提交和审核是同一条链。转给探索 agent，提交和审核仍然分开。

**防止来回打转**：同一媒体、同一平台编号，审核 agent 只驳回并改正一次。按这条线索重新提交的单如果又没过证据门，
只能放行或维持人工。

### 5. 证据门：第一步失败也跑第二步

`evaluateEvidenceGate` 第一步不通过时，现在直接返回，`step2: null`。改为照样跑第二步，结果记进 `evidence.gate.step2`，
结论不变（仍是 `needs_review`）。这样审核 agent 和审核员都能看到全部冲突，第 4 节的复核也有现成的第二步可用。

### 6. 模型、工具和预算

和探索 agent 相同：经 magpie，一张单一个会话，用 `exploration-tools.ts` 里的查询工具
（`get_collection`、`get_catalog_season`、`get_catalog_entry`、`resolve_link`、`search_catalog`、`web_search`、`web_fetch`），
结论工具换成第 2 节的三个。首轮预填变更单、证据门的冲突和已拉到的证据。

审一张单比探索的事少，起始值：每单 16 步、2 分钟、30 万 token，留收尾阶段，用环境变量配置。
token 计入当天的 `exploration_daily_budget.pi_usage`，和探索共用每日 token 上限，一起上报 tokens.ci。
另有每日审核张数上限 `REVIEW_AGENT_DAILY_BUDGET`，上线时为 `"0"`，评测后再开。

### 6.1 分集上下文和平台集号

平台集号指合集正片列表里的**位置**（从 1 数），不是标题里的编号。适配器（如哔哩哔哩 `index: episodes.length + 1`）、
证据门第二步、按集查询（`targetEpisode = targetEpisodeStart + 偏移`）和下游的弹幕取集
（rex-widget `scraper-kit` 跳过预告和黑名单标题后按顺序编号）都是这样数的。

审核 agent 两边都看，判断夹在中间的额外内容有没有让对应错位：

- `get_collection` 每一集给出位置、`title`、`longTitle`（现在只给其中一个）、播出日期、时长；
- `get_catalog_season` 现在只给集数和年份，改为也给每一集的集号、标题、播出日期，第 0 季同样可查。

提示词附上案例。例如灵笼第一季：哔哩哔哩的 16 条正片依次是 001–006、中章、007–012、终章上、终章下、特别篇，
TMDB 第 1 季 12 集，中章、终章、特别篇在第 0 季。整季从第 1 集起一一对应时，位置 7 是中章，
TMDB 第 7–12 集会对到位置 7–12，错开一位；对齐的分段是第 1–6 集对位置 1–6、第 7–12 集对位置 8–13。
额外内容排在末尾（不在中间）时，整季一段即可。

### 7. 页面

- 变更单页：审核人是 `system:review-agent` 时显示「审核 agent」而不是「审核员」，显示它的理由；
  驳回并改正时显示改正后的季和分段。
- `/review` 队列：维持人工的单显示审核 agent 的意见。
- 审核员可以按审核人筛出审核 agent 放行的单抽查，必要时用现有操作回退。

## 实施顺序

每步一个 PR。

1. 证据门规则：去掉「最终季」和片名尾的年份；年份按提交那段的集的播出年份比。
2. 证据门第一步失败也跑第二步（第 5 节）。
3. 分集上下文：`get_collection`、`get_catalog_season` 的分集输出（第 6.1 节）。
4. 审核 agent 执行器：任务类型、三个结论工具、放行条件，只做放行和维持人工，`REVIEW_AGENT_DAILY_BUDGET = "0"`。
5. 驳回并改正：第二步复核、线索、需求不退避、只改正一次。
6. 页面（第 7 节）。
7. 用审核员处理过的 `needs_review` 单做评测集离线重放，看放行的误判率，确认后再开。

## 未决

- 线上 `needs_review` 队列里各冲突码的数量还没统计，第 6 节的预算是估的。

## 后果

- 证据门的漏判（对的单被卡）大部分交给模型和第 3 节的代码检查兜底，审核员只看剩下的。
- 放行依赖模型判断，误放行的代价是一条错关联生效；靠评测、抽查和回退控制。
- 错的提交会变成线索，由探索 agent 重新提交，用户提交错了季也能得到正确的关联。
- 「证据门」不再等于「自动审核」的全部：GLOSSARY 增加「审核 agent」，「线索」也包括审核 agent 的改正。
